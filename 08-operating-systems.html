Processes, Threads & IPC

Processes, PCB & System Calls

A process is a program in execution — its own address space, registers, and resources. The OS keeps each process's bookkeeping in a Process Control Block (PCB).

PCB fieldContents
Process statenew, ready, running, waiting, terminated
Program counteraddress of next instruction
CPU registerssaved when the process loses the CPU
Scheduling infopriority, pointers to scheduling queues
Memory & I/O infobase/limit or page table pointer; open files

A system call is the only way a user program requests a kernel service (I/O, file, process, memory). It causes a trap/software interrupt, switching the CPU from user mode to kernel mode; the mode bit (0 = kernel, 1 = user) is the hardware safeguard that prevents the user from executing privileged instructions directly.

Process state transitions to memorise
Ready → Running (CPU dispatched to the process) · Running → Ready (preempted / quantum expiry)
Running → Waiting (I/O request, waits for event) · Waiting → Ready (event completes)
Running → Terminated · Ready → Waiting is IMPOSSIBLE (a waiting—not ready—process cannot go straight to I/O).
GATE trap
Only Ready ↔ Running and Running → Waiting → Ready are driven by the scheduler/events. A process in the Ready queue cannot perform I/O, and a process in Waiting is not using the CPU. The PCB does not store the program's source code — only its runtime context.

Threads

A thread is a single flow of execution within a process. Threads of one process share the address space, open files and process resources, but each has its own program counter, register set and stack.

ItemOwned by each threadShared by threads of a process
Program counteryes
Register setyes
Stackyes
Heap / address spaceyes
Open files / resourcesyes
  • User threads (thread library) are invisible to the kernel — fast but a blocking syscall blocks them all.
  • Kernel threads are managed by the OS — each can be dispatched independently; slower to create.
  • Threads switch faster than processes (context is smaller, address space is shared).
GATE trap
Threads of the same process share memory but do NOT have their own address space. A change to a shared variable by one thread is visible to the others — this is exactly why synchronisation is needed. Don't confuse a thread's private stack with the shared heap.

Inter-Process Communication (IPC)

IPC lets processes exchange data. Two fundamental models: shared memory (fast, user-managed synchronisation) and message passing (kernel-mediated, send/receive).

MechanismModelKey fact
Shared memorymapping a common regionno kernel copy; needs explicit sync
Message passingsend/receivemessage queues; kernel buffers involved
Pipesmessageone-way; size-bounded buffer
Socketsmessageused for network & local IPC
Shared-file / signals—signals deliver events to a process
GATE trap
Named pipes (FIFOs) persist and can connect unrelated processes; anonymous pipes exist only between parent and child. Classic producer–consumer and bounded-buffer problems are used to test whether you remember that the buffer, not the message-passing subsystem, is the shared resource needing locks.

CPU Scheduling

Scheduling Policies

The scheduler chooses the next process from the ready queue. Non-preemptive = a process keeps the CPU until it yields (I/O or terminate); preemptive = the OS can take the CPU away (e.g. at a time quantum, or when a higher-priority process arrives).

PolicyPreemptive?RuleKey fact
FCFSNofirst-come first-servedconvoy effect possible
SJF (non-preemp.)Noshortest next burstoptimal avg waiting time
SRTF (SJF preemptive)Yesrem. burst, preempt on arrivaloptimal avg waiting too
PriorityBothhighest priority firstmay starve low-priority tasks
Round RobinYeseach ready process gets q timefair; of q too big resembles FCFS
Multilevel queue / MLFQYesgrouping + agingaging prevents starvation
  • Aging (increase priority with age) is the standard fix for starvation in priority & MLFQ.
  • SJF requires knowing the CPU burst length, which is usually unknown — it is a theoretical optimum.
  • Smaller time quantum q → better response time but more context-switch overhead.

Scheduling Metrics & Worked Example

The four numbers that dominate scheduling questions
Turnaround = Completion − Arrival  ·  Waiting = Turnaround − Burst = Completion − Arrival − Burst
Response = First-CPU-time − Arrival  ·  CPU utilization = busy/(busy + idle)
One-line rule
The only tricky piece is waiting: compute completion − arrival − burst, never completion − burst (that forgets the arrival-time offset the question may include).
Worked example — FCFS, SJF, RR(q=3) and Priority on one dataset

Processes (arrival, burst): P1(0,8), P2(1,4), P3(2,9), P4(3,5).

FCFS

Order P1,P2,P3,P4. Completions: P1=8, P2=12, P3=21, P4=26. Waiting = completion−arrival−burst: 0, 7, 10, 18 → avg = 35/4 = 8.75. Turnaround: 8, 11, 19, 23 → avg 15.25.

SJF (non-preemptive)

P1 runs first (only one ready at t=0) → CT 8. Then shortest available: P2(4) CT12, P4(5) CT17, P3(9) CT26. Waiting: P1=0, P2=7, P4=9, P3=15 → avg = 31/4 = 7.75 (better than FCFS, as theory predicts).

Round Robin, q = 3

Ready queue in arrival order; preempt after 3 units.
P1[0–3]→P2[3–6]→P3[6–9]→P4[9–12]→P1[12–15]→P2[15–16 done]→P3[16–19]→P4[19–21 done]→P1[21–23 done]→P3[23–26 done]. Completions: P1=23, P2=16, P3=26, P4=21. Waiting: 15, 11, 15, 13 → avg = 54/4 = 13.5. Turnaround: 23,15,24,18 → avg 20.

Priority (lower number = higher priority)

Priorities P1=3, P2=1, P3=4, P4=2 (non-preemptive). P1 runs first (arrived at 0); then P2, P4, P3. Completions same as SJF ordering: P2=12, P4=17, P3=26; waiting avg 7.75.

Takeaway: SJF (and priority ordering by burst here) gives the lowest waiting time. RR's wait time depends as much on q and arrival spread as on burst lengths.

Concurrency & Synchronisation

Critical Section & Locks

The critical section is the code region touching shared data — only one process may be inside it at a time. Three classic requirements:

  1. Mutual exclusion — at most one process in the CS at a time.
  2. Progress — if no process is in the CS and some want to enter, one must be able to (the choice cannot be postponed forever by processes outside the CS).
  3. Bounded waiting — a bound on how long a process waits to enter after requesting.
Hardware/software building blocks
Test-and-set and compare-and-swap are atomic instructions used to build a spinlock.
Peterson's algorithm solves the 2-process CS using flags + a turn variable (no hardware support).
A spinlock busy-waits (wastes CPU) — suited to short CS on multi-core; otherwise use blocking locks.
GATE trap
Mutual exclusion alone is not enough. A solution can allow mutual exclusion yet violate progress or bounded waiting (the classic two-process flag-only solution can deadlock/starve). GATE often gives a code snippet and asks which requirement it violates — check all three, not just mutex.

Semaphores, Monitors & Classical Problems

PV semantics
wait(S) / P(S): if S > 0 then S ← S−1, else the caller is blocked on S.
signal(S) / V(S): S ← S+1; if a process was blocked on S, one is woken.
If the initial value is 1 it is a binary semaphore (mutex); value ≥ 1 is a counting semaphore.
A counting semaphore initialised to k allows at most k processes inside simultaneously.

Monitors are language-level constructs with automatic mutual exclusion: only one process may be active inside a monitor procedure at a time; condition variables (wait/signal on a condition) implement synchronisation. Producer–consumer uses two counting semaphores (empty, full) plus a mutex; readers–writers lets many readers in together while writers get exclusive access.

Worked example — maximum value & blocking of a counting semaphore

A counting semaphore S is initialised to 3.

  • At most 3 processes can be inside their critical section simultaneously without blocking.
  • The semaphore value can never go negative under correct PV use — P decrements only when S > 0, otherwise it blocks; so the minimum value is 0 and the number of blocked processes is not stored in S.

Numeric: start S = 5. Perform P, P, V, P, P, P, V. Then S = 5 − 3 + 2 = 4 after the three P and two V (net −1). Each waiting P either succeeds (S>0) or blocks the caller.

Worked example — classic PV mutual exclusion reasoning

Two processes share a variable; a binary semaphore mutex = 1.
Entry: P(mutex); Critical section; Exit: V(mutex).

If P1 enters the CS, mutex drops to 0. P2 executing P(mutex) finds S=0 and blocks until P1 executes V(mutex), which wakes P2 with S←1. This guarantees mutual exclusion.
Order trap: if two P calls are swapped (e.g. P(empty); P(mutex) instead of P(mutex); P(empty)), a classic deadlock can arise — a favourite GATE question.

Deadlock

Conditions, Handling & Resource Allocation

Deadlock = a set of processes each holding a resource and waiting for a resource held by another in the set. Four necessary conditions (all four must hold):

  1. Mutual exclusion — resources are non-sharable.
  2. Hold and wait — holding a resource while waiting for another.
  3. No preemption — a held resource cannot be forcibly taken.
  4. Circular wait — a cycle of processes each waiting on the next's resource.
Handling strategies
Prevention — break one condition (e.g. request all resources at once ⇒ removes hold-and-wait).
Avoidance — decide before granting whether the resulting state is safe (Banker's).
Detection & recovery — let it happen, then find cycles in the wait graph and abort/preempt.
Ostrich — ignore (the OS assumes deadlock is rare).
GATE trap
Hold-and-wait prevention by "request all at once" reduces resource utilisation (a process holds everything it might ever want). Circular-wait is broken by imposing a total ordering on resource types and requesting in that order. Removing any one of the four conditions prevents deadlock — GATE asks which single condition a given technique removes.

Banker's Algorithm (Avoidance)

Banker's uses Max and Allocation per process, plus system-wide Available. Need = Max − Allocation. A state is safe if there exists a sequence of processes that can each finish using the currently available resources (available + resources released by completed processes).

Safety check — how to do it under time pressure
  1. Compute Need = Max − Allocation for every process.
  2. Start Work = Available.
  3. Find a process whose Need ≤ Work; pretend it runs, set Work += its Allocation; mark it done.
  4. Repeat. All processes done ⇒ safe (a safe sequence exists); otherwise a cycle ⇒ unsafe (will deadlock).
Pass a request only if the resulting state is safe.
Worked example — full Banker's safety run

Resources A,B,C. Available = (3,3,2). Allocation / Max:

ProcAllocMaxNeed
P0(0,1,0)(7,5,3)(7,4,3)
P1(2,0,0)(3,2,2)(1,2,2)
P2(3,0,2)(9,0,2)(6,0,0)
P3(2,1,1)(2,2,2)(0,1,1)
P4(0,0,2)(4,3,3)(4,3,1)

Work = (3,3,2).
P1 need (1,2,2) ≤ Work → run, Work = (5,3,2) · P3 need (0,1,1) ≤ Work → Work = (7,4,3) · P4 need (4,3,1) ≤ (7,4,3) → Work = (7,4,5) · P0 need (7,4,3) ≤ Work → Work = (7,5,5) · P2 need (6,0,0) ≤ Work → Work = (9,5,7).

Safe sequence: P1,P3,P4,P0,P2 — hence the current state is safe.

Test a request P0 asks for (0,2,0): tentative Available = (3,1,2), P0 Need becomes (7,2,3).
Work=(3,1,2): P3 (0,1,1)≤→(5,2,3) · P1 (1,2,2)≤→(7,2,3) · P0 (7,2,3)≤→(7,3,3) · P4 → (7,3,5) · P2 → safe. Grant it.

Memory Management

Contiguous Allocation & Paging

  • Contiguous allocation: each process gets one continuous region. Fragmentation from variable-size holes ⇒ allocate externally (external fragmentation). Base + limit registers relocate a process.
  • Paging: physical memory split into equal frames, logical memory into equal pages. A page table maps page → frame. No external fragmentation; only internal fragmentation (last page partial).
  • Segmentation: variable-size segments (code, data, stack) — matches user view but reintroduces external fragmentation; uses segment table with base/length.
  • TLB is a fast associative cache of recent page-table entries (TLB hit avoids a memory access for the page table).
Address split & size formulas
Logical addr = page number + offset. Offset bits = log₂(page size). Page-number bits = (addr bits) − offset bits.
Page table size = (number of pages) × (bytes per entry).  ·  Number of frames = physical memory / frame size.
TLB effective access time: EAT = h·(TLB + mem) + (1−h)·(TLB + 2·mem), for TLB hit ratio h.
GATE trap
Paging gives internal fragmentation; contiguous allocation and segmentation give external fragmentation. Swapping them in a "which is true" question is an annual trap. Also, the total logical-page space can far exceed physical memory — that is precisely why virtual memory (subsection 7) exists.

Address Translation — Worked Example

Worked example — page offset bits and TLB effective access time

(a) Bits. Logical address = 32 bits, page size = 4 KB = 2¹² bytes ⇒ offset bits = 12, page-number bits = 32 − 12 = 20; a fully paged space has 2²⁰ logical pages.

(b) TLB. Memory access = 100 ns, TLB access = 20 ns, hit ratio = 0.95 (page always resident).
EAT = 0.95·(20+100) + 0.05·(20+100+100) = 0.95·120 + 0.05·220 = 114 + 11 = 125 ns.

(c) Page table memory. With 2²⁰ pages and 4-byte entries, page table = 2²⁰ × 4 = 4 MB per process. This is why multi-level page tables and TLB caching exist.

Faster EAT by hand
Don't expand the TLB formula into fractions. Write hit×fast + miss×slow directly where fast = TLB+mem and slow = TLB+2·mem (page table walk). Set the hit ratio as a decimal, compute the two products, add. Always check your answer is between fast and slow — a common sanity test.

Virtual Memory & Page Replacement

Demand Paging & VM Concepts

Virtual memory allows a process to run even if its logical space exceeds physical memory. With demand paging, a page is brought in only when referenced (a page fault triggers a load). The valid/invalid bit in the page table marks whether a page is resident.

Effective access time with page faults
EAT = (1 − p)·tmem + p·tfault, where p = page-fault rate, tfault = time to service a fault.
Fault rate = faults / total references.
TermMeaning
Page faultreferenced page not in memory → load it (expensive)
Copy-on-writechild's pages shared with parent, copied only on write — fast fork()
Thrashingprocess has fewer frames than its working set ⇒ constant faulting, near-zero CPU use
Working setthe set of pages a process touches in the recent window
Page size trade-offlarger pages ⇒ fewer table entries but more internal fragmentation & I/O
GATE trap
Thrashing is NOT a shortage of CPU or of memory bandwidth — it is a shortage of frames relative to the working set, causing a page-fault storm. Increasing the degree of multiprogramming can make thrashing worse, not better. Also: an LRU approximation via reference bit is used in practice because true LRU (a stack) is too expensive to maintain.

Page Replacement Algorithms — Worked Example

Frame selection on a page fault: FIFO evicts the oldest-loaded page; LRU evicts the least-recently-used; Optimal evicts the page whose next use is farthest in the future (needs the whole reference string — a theoretical lower bound, not implementable).

What GATE asks you to memorise
Optimal cannot be beaten (minimum possible faults) · FIFO exhibits Belady's anomaly (more frames ⇒ more faults) · LRU and Optimal are stack algorithms (never suffer Belady's).
Typical fault order for the same string, 3 frames: Optimal < LRU < FIFO.
Worked example — FIFO vs LRU vs OPT on one reference string

Reference string 7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1, 3 frames.

FIFO (queue order): faults at 7,0,1,2,3,0,4,2,3,0,1,2,7,0,1 → 15 faults.
Evicts: 7,0,1,2,3,0,4,2,3,0,1,2,7,0,1.

LRU (evict least-recently-used): faults at 7,0,1,2,3,4,2,0,1,0,7 → 12 faults (evicts 7,1,2,3,0,4,0,3,0,2 in that sense of LRU). Track recency after every hit — that is the hard part.

Optimal (evict page with farthest next use): faults at 7,0,1,2,3,4,0,1,7 → 9 faults (evicts 7,1,2,4,3,2 at the fault points). Optimal < LRU < FIFO, as expected.

Belady's anomaly — a 4-frame FIFO beats 3 frames (or does it?)
For string 0 1 2 3 0 1 4 0 1 2 3 4:
FIFO with 3 frames → 9 faults; FIFO with 4 frames → 10 faults. Increasing frames increased faults! That is Belady's anomaly, impossible for LRU or Optimal.

File Systems & Disk I/O

Files, Directories & Allocation

A file is data with a name, stored on secondary storage organised into blocks/sectors. The inode (Unix) holds a file's metadata and the block pointers that locate its data.

Allocation methodProsCons
Contiguousfast, minimal overhead, directexternal fragmentation, hard to grow
Linked (chain)no external frag, easy growthrandom access slow (must follow links)
Indexedfast random accessindex-block overhead (file table fat)
GATE trap
Disk traps: a single-level directory does not allow the same file name in different subdirectories — a two-level (user + file) or hierarchical directory does. FAT/tables are fine, but GATE likes to test whether you know linked allocation makes random access O(n) and contiguous allocation causes external fragmentation. Also disk sector is the minimum I/O unit, not a byte.

Disk Scheduling — Worked Example

Seek strategies on a head at cylinder c
FCFS = serve in request order · SSTF = nearest cylinder first (may starve far ones, may be non-optimal)
SCAN (elevator) = move one direction servicing all, then reverse · C-SCAN = service one direction, jump back to start (more uniform wait) · LOOK / C-LOOK = SCAN but reverse only as far as requests exist.
Worked example — FCFS and SSTF with a head at cylinder 50

Head starts at 50. Queue: 90, 20, 75, 35, 60.

FCFS movement: 50→90(40)→20(70)→75(55)→35(40)→60(25) = 230 head movements.

SSTF: always step to the nearest pending request — 50→60(10)→75(15)→90(15)→35(55)→20(15) = 110 head movements. (SSTF ≈ half of FCFS here, which is typical.)

SCAN moving toward larger then reversing at the highest request: 50→60→75→90 (40 up), then 95→35(55)→20(15) descending = 40 + 55 + 15 = 110 — same total, but the served order differs, which changes waiting times. SCAN never lets the head dart back and forth; SSTF can.

Exam shortcut
For seek questions, only the absolute |screen| differences matter. List the head position, then add each movement; never re-read the queue. SSTF usually gives the smaller total than FCFS, and C-SCAN gives uniform waiting at the price of the long return jump.

Exam Strategy

Attempt order for OS
  1. Scheduling numerics first (fastest, most reliable marks) — draw the Gantt chart then fill the table.
  2. Page replacement / TLB numerics next — deterministic once you track frames/reference bits.
  3. Deadlock + synchronisation concepts — high accuracy, quick to verify against the four conditions / PV rules.
  4. File I/O, fragmentation, definitions last — know the two-line facts, don't dive into edge cases.

What to skip under time pressure

  • Odd multi-process fork() counting and reader–writer code variants with subtle scheduling — high time cost, small reward; return only if everything else is done.
  • Long Banker's safety runs on 5+ processes if a shorter question is pending — steps are mechanical, but they eat minutes; answer the 1-mark version instead.
  • Disk SCAN with boundary details if ambiguous — the question usually pins down the direction; if not, state your assumption and move on.

Common time sinks & how to avoid them

  • Redrawing tables: keep one extra column for arrival in scheduling — it is the thing you forget.
  • Re-simulating page replacement: a 20-reference string traced twice wastes 3+ minutes; trace once, top-down, and track the frame set in a compact grid.
  • Ambiguous "which is/which statement is true" — read all four options before choosing; distractors in OS are usually one word off (internal vs external, prevention vs avoidance, thread vs process).
  • For NAT questions, no negative marking: an educated guess on a numeric (e.g. 8.75, 12) is free — always submit something inside the plausible options, never a blank.
