Overview & Weightage

Marks 8 / 100 Typical Qs 5–7 Sections 9 Scoring High yield, formula-driven

Databases is one of the most predictable core subjects. Most questions are re-skinned versions of a small set of recurring themes: candidate-key hunting, normal-form classification, relational-algebra/SQL output, B/B+ tree arithmetic, and transaction-schedule analysis. These five themes account for roughly 70% of the marks and are all mechanical once the method is memorised.

ER Model & Mapping to Relations

ER Concepts & Relationships

The ER model describes a database as entity sets, attributes and relationships.

ElementMeaning
Entity setcollection of real-world objects sharing attributes (a rectangle)
Attributesimple / composite / multi-valued / derived (oval)
Relationshipassociation between entity sets (a diamond)
Cardinality1:1, 1:N, N:1, M:N between participating entity sets
Key (primary)attribute(s) uniquely identifying each entity (underlined)
Weak entityno key of its own; depends on an owner via a total, identifying relationship
Participationtotal (every entity participates, needed for weak) vs partial

Mapping cardinality constraints to relations

  • 1:1 — merge into one relation (put the other's key + attributes into one side) OR keep two relations with a FK either way.
  • 1:N — put the key of the "one" side as a foreign key in the relation of the "N" side, plus any relationship attributes.
  • M:N — create a separate junction/jackson relation whose key is the combination of both entity keys (+ relationship attributes).
  • Weak entity — its relation's primary key = owner's key + its partial/ discriminator key.
Quick test for cardinalities
Ask "can one X have many Y?" in both directions. 1:N = one of A can own many of B but not vice-versa; M:N = both directions allow many. Every GATE ER mapping question reduces to picking the ≥2-table rule correctly.
GATE trap
Do not confuse cardinality with participation. "One student is enrolled in many courses" is a cardinality fact; "every course has at least one student" is a participation (total vs partial) fact. A weak entity must have total participation in its identifying relationship — that is the entire basis of the weak-entity rule.

ER → Relational Mapping Rules

Mapping rules (Condensed)
  • Each entity set → one relation. Primary key = entity key.
  • Multi-valued attribute → its own relation with key = (owner's key ∪ attribute).
  • Composite attribute → flattened into its component simple attributes.
  • 1:1 / 1:N / M:N → rule in the box above.
  • Specialisation/generalisation → option of overlapping/disjoint; may map each subclass to its own relation (with its own extra attributes) sharing the superclass key.
Worked example — map a 1:N relationship with attributes

Entity sets Employee(EID, Name) and Department(DID, Dname), relationship Works-in (1:N; a department has many employees) with attribute Since.

Rule for 1:N: put DID (key of the "one" side) into the "many" side relation, plus relationship attributes.

Result:
Employee(EID, Name, DID, Since) and Department(DID, Dname).
Here DID in Employee is a foreign key referencing Department.

GATE trap
For an M:N relationship students wrongly put a FK into one of the existing relations. That is illegal — it would force one-to-many and lose information. The M:N rule always creates a third relation, and its primary key is the concatenation of the two entity primary keys. Losing the relationship's own attributes is another classic error.

Relational Model & Integrity Constraints

Keys in the Relational Model

A relation is a set of tuples (no duplicate rows), each defined over a schema of attributes.

Key typeDefinition
Superkeyany set of attributes that uniquely identifies a tuple (may have redundancy)
Candidate keya minimal superkey (no proper subset is a superkey)
Primary keythe chosen candidate key; not NULL
Foreign keyattribute(s) referencing the primary key of another relation
Finding candidate keys — closure method
The closure X⁺ of attribute set X under a FD set F is all attributes reachable by repeatedly applying each X→Y in F when X ⊆ current set.
Left-only rule: any attribute appearing only on the left of every FD (never on a right side) must be in every candidate key. Compute its closure; if it covers all attributes it is the key.
Worked example — find all candidate keys of R(A,B,C,D,E)

FDs: AB→C, C→D, D→B, DE→A.
Left-only rule: A appears only on a left side, and E appears only in DE (left side), so both must be in every candidate key.

Compute (A,B,E)⁺: start {A,B,E} → apply AB→C ⇒ add C → {A,B,C,E} → apply C→D ⇒ add D → {A,B,C,D,E} = all. So {A,B,E} is a candidate key. Minimality: remove B gives {A,E}, whose closure cannot reach B or C or D (no FD's left side is a subset of {A,E}), so B is required.

Answer: {A, B, E}.

GATE trap
A superkey is NOT a candidate key until you prove minimality. Common error: stopping once the closure covers everything and reporting a non-minimal superset. Always check that removing any single attribute breaks the closure. Also the left-only rule alone is necessary, not sufficient — you still must close the set to confirm it is a key.

Integrity & Constraints in SQL

Integrity constraints guard the database state:

ConstraintMeaningViolation example
Entity integrityprimary key values can never be NULLtwo rows with a NULL PK
Referential integrityevery foreign-key value is either NULL or matches an existing primary-key valueFK = 99 with no PK = 99
Domain / typeattribute values come from a fixed domainAge = "abc"
NOT NULLattribute can't be NULL—
UNIQUEno duplicate values (but NULLs allowed, multiple)duplicate email
CHECKarbitrary boolean condition on valuesAge < 0

Referential-integrity actions on delete/update of the referenced row

  • NO ACTION / RESTRICT — reject the deletion/update if child rows reference it.
  • CASCADE — delete/update the child rows too.
  • SET NULL — set the FK to NULL in child rows.
  • SET DEFAULT — set FK to its default value.
GATE trap
In SQL, a foreign key value may be NULL by default — referential integrity only requires non-NULL FKs to match. This surprises students who expect every FK to be validated. Also: a UNIQUE column can hold multiple NULLs in SQL (unlike primary keys, which cannot be NULL at all).

Relational Algebra & Tuple Calculus

Relational Algebra & Output Prediction

Algebra operators take relations and return a relation (a set — duplicates removed).

OperatorSymbolWhat it returns
Selectionσcond(R)row subset (rows matching condition)
Projectionπlist(R)column subset, deduplicated
UnionR ∪ Srows in R or S (compatible schemas)
Set differenceR − Srows in R, not in S
IntersectionR ∩ Srows in both (≡ R − (R − S))
Cartesian productR × Sall pairs of rows
Natural joinR ⋈ Srows joined on equally-named attributes
Theta joinR ⋈θ Sjoin on any condition θ (eq-join = θ equi-join)
Renameρrename relation or attributes
DivisionR ÷ Sall x in R paired with every y of S
Cost & equivalence facts
  • σc1∧c2(R) ≡ σc1(σc2(R)) — cascade selection.
  • πA(σc(R)); push selection before join to shrink work.
  • Selection is commutative and distributes over join: σc(R⋈S) ≡ σc(R)⋈S when c references only R.
  • Selection vs projection are not always interchangeable (σ selects rows, π removes columns).
  • An M:N relationship query ("suppliers who supply all parts") is the canonical division query.
Worked example — predict the exact output rows

Employee(EID, Name, Salary, DeptID):
(1, Alice, 50000, 10) · (2, Bob, 60000, 10) · (3, Carol, 55000, 20) · (4, Dave, 70000, 20)

Evaluate πName(σSalary>52000 ∧ DeptID=20(Employee)).

Selection first: Salary > 52000 → Bob, Carol, Dave; then DeptID = 20 → Carol, Dave.
Projection on Name → {Carol, Dave}. Because result is a set, order and the count (2 rows) are the deliverable.

GATE trap
π (projection) removes duplicates, so counting rows in a projection is ≤ the number of matching rows. In output prediction, students forget the dedup and over-count. Also note σ before π in this pattern: σ is applied first, then π — swapping them usually changes nothing here but order matters when a column condition is on a dropped column.

Tuple & Domain Relational Calculus

Tuple relational calculus (TRC): declarative — describe the answer as { t | condition }, "tuples t such that…". Domain relational calculus (DRC): same idea over attribute domains (variables). Neither specifies how to compute, only what the result is — this is non-procedural, unlike relational algebra.

FeatureRelational algebraRelational calculus
Natureprocedural (steps)declarative (description)
Expressive powerrelational-completesame (with safe queries)
Key quantifiers—∃ (there exists), ∀ (for all)
Typical TRC patterns
  • Exists-style: { t | ∃s ∈ Student (t.Name = s.Name ∧ s.Dept = 'CSE') } — a select-project style query.
  • Universal-style ("all": supplies all parts): { s | ∀p ∈ Parts (∃c ∈ Supply (c.SupplierId = s.Id ∧ c.PartId = p.Id)) }.
  • A query expressible without ∀/∃ iteration is called a safe query and identifies the division idiom.
GATE trap
∀ is the "supplies all" quantifier — not ∃. The single most common calculus mistake is writing ∃ where the question asks for "every / all". Also, calculus can be expressed algebraically and vice-versa: the two are equivalent in power, so expecting a calculus-only feature is wrong.

SQL — Queries & Output

Select, Aggregation, Joins

SQL query execution order that determines output:

  1. FROM (tables + joins)
  2. WHERE (row filter)
  3. GROUP BY (group rows)
  4. HAVING (filter groups)
  5. SELECT (projection / aggregate)
  6. ORDER BY (sort, last)
Aggregates & the NULL subtleties
COUNT(*), COUNT(col), SUM, AVG, MIN, MAX.
  • COUNT(col), SUM, AVG ignore NULLs; COUNT(*) counts all rows including NULL.
  • AVG of attr = SUM/COUNT(attr) (NULLs dropped) — not SUM/count of rows.
  • If every value of a column is NULL: SUM → NULL, AVG → NULL, COUNT(col) → 0.
  • DISTINCT removes duplicates before aggregation: COUNT(DISTINCT dept).
WHERE vs HAVING quick rule
WHERE filters rows before grouping; HAVING filters groups after grouping. You cannot use an aggregate in WHERE, only in HAVING (or SELECT). A classic error: writing "Salary > AVG(...)" in WHERE.
ClauseFiltersAggregates allowed?
WHERErows (pre-grouping)No
HAVINGgroups (post-grouping)Yes
SELECToutput columnsYes
ORDER BYsorts final resultYes-ish
Worked example — GROUP BY + HAVING output

Enable table Emp(EID, Dept, Sal): (1, A, 100), (2, A, 200), (3, B, 300), (4, C, 100).

SELECT Dept, COUNT(*) FROM Emp GROUP BY Dept HAVING COUNT(*) ≥ 1;

Grouping: A→2 rows, B→1, C→1. HAVING COUNT(*)≥1 keeps all groups (all have ≥1).
Output: (A, 2), (B, 1), (C, 1) — three rows, and note no NULL or dedup surprises here.

Nested, Correlated & Set Queries

Set operator semantics
UNION (dedup, default), UNION ALL (keep dupes), INTERSECT (common), EXCEPT / MINUS (in first, not second). For set operators the two subqueries must be union-compatible (same arity & compatible types).
  • NOT EXISTS and NOT IN are the classic "division / all" idioms in SQL.
  • A correlated subquery references an outer-table column; it is re-evaluated for every outer row (expensive, but often the only way to express "per-row" conditions).
  • EXISTS returned when at least one row satisfies the inner query — that inner query's SELECT list is ignored.
GATE trap
NOT IN vs NOT EXISTS differ on NULLs. If the subquery can return NULL, NOT IN evaluates to unknown for those rows and may return an empty result, whereas NOT EXISTS behaves correctly. This NULL landmine is a recurring SQL question. Prefer NOT EXISTS.
Worked example — correlated subquery (emps with a higher-paid colleague)

SELECT e.Name FROM Emp e WHERE e.Sal > (SELECT AVG(s.Sal) FROM Emp s WHERE s.Dept = e.Dept AND s.EID ≠ e.EID);

The inner AVG is recomputed per outer row e: it averages only the other employees in e's own department. This is a correlated query because e.Dept (outer alias) appears inside the subquery. Rows whose salary exceeds their colleagues' average are returned.

Functional Dependencies & Normal Forms

Functional Dependencies & Keys

An FD X→Y means: any two tuples with equal X must have equal Y. FDs are the raw material for defining keys and normal forms.

Armstrong's axioms (sound & complete)
  • Reflexivity: if Y ⊆ X then X→Y.
  • Augmentation: X→Y ⟹ XZ→YZ.
  • Transitivity: X→Y and Y→Z ⟹ X→Z.
Derived: Union (X→Y, X→Z ⟹ X→YZ), Decomposition (X→YZ ⟹ X→Y), Pseudo-transitivity. X→Y is trivial if Y ⊆ X. The closure X⁺ = set of all attributes implied by X using the FD set.
Worked example — compute the closure X⁺

FDs: AB→C, C→D, D→B, DE→A. Find C⁺.

Start {C}. Apply C→D → add D ⇒ {C,D}. Apply D→B → add B ⇒ {C,D,B}. Nothing else applies (AB needs A; DE needs E). So C⁺ = {C,D,B}. Because C⁺ excludes A and E, C is not a superkey.

Normal Forms — How to Classify

To state the highest normal form of a relation: check each level in order.

FormConditionViolation that demotes it
1NFatomic (single-valued) attributesmulti-valued / nested tables
2NF1NF + no partial dependency (no non-prime attr on a proper subset of a candidate key)A→B where A ⊂ key, B non-prime
3NF2NF + no transitive dependency (there is no FD X→Y with X not a superkey and Y a non-prime attr)key→A and A→B (B non-prime)
BCNFevery FD X→Y has X a superkeyany X→Y with X not superkey

Prime attributes = attributes that belong to some candidate key. A dependency's left side is checked against superkeys, its right side against prime/non-prime status.

Classification shortcuts
  • BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF. Each is a strict subset.
  • 2NF failure ⟺ some candidate key is composite and a non-prime attr depends on part of it.
  • If every candidate key is a single attribute, the relation is automatically at least 2NF (no partial dep possible).
  • 3NF test per FD: X→Y must have X superkey or Y prime.
  • BCNF test per FD: X must be a superkey, no excuses.
Worked example — find highest normal form of R(A,B,C)

FDs: A→B, B→C. Candidate keys: {A} (A⁺ = {A,B,C}). Prime attr: A. Non-prime: B, C.

1NF ✓ (atomic). 2NF: no partial dep since the key {A} is a single attribute ✓.
3NF: check B→C — B not superkey, and C is non-prime; so X→Y with X not superkey and Y non-prime = transitive dep → NOT 3NF. BCNF fails for the same reason.

Answer: highest normal form = 2NF.

GATE trap
Students jump straight to BCNF and stop at the first non-superkey FD, mis-labelling a 2NF relation as 3NF. The prime-attribute escape matters: if Y is prime, the FD does not violate 3NF (but still violates BCNF). Always check 3NF before concluding BCNF — BCNF is the strictest, not the default answer.

Decomposition — Lossless & Dependency-Preserving

A decomposition R → {R1, R2, …} must satisfy two independent properties:

The two decomposition tests
  • Lossless (lossless-join): natural-joining R1, R2 … recovers R exactly. For a 2-relation decomposition, lossless ⟺ R1 ∩ R2 is a superkey of R1 or R2.
  • Dependency-preserving: the union of the FDs that hold in each component is equivalent to the original FD set (no FD is lost when the tables are separated).
BCNF always has a lossless decomposition, but it may not preserve dependencies. 3NF has a decomposition that is both lossless and dependency-preserving.
Worked example — decompose R(A,B,C), A→B, B→C, to BCNF

Key {A}. Violating FD: B→C (B not superkey). Decompose on B→C into R1(B,C) and the remainder R2(A,B).

Check lossless: R1 ∩ R2 = {B}; B is the key of R1 → lossless ✓.
Check dependency-preserving: A→B (in R2) ✓, B→C (in R1) ✓, A→C redundant (derived) ✓ → preserves.

Both R1 and R2: BCNF (each candidate key single-attribute). Result: R1(B,C), R2(A,B).

GATE trap
If and only if the components overlap on a superkey does the decomposition survive a natural join. A decomposition that is dependency-preserving is not automatically lossless, and vice-versa — GATE deliberately pairs one theory (lossless, not preserving) against the other (preserving, not lossless). Test them separately.

File Organisation & Record Access

Heap, Sorted, Hash & Indexed Files

OrganisationLookupInsertNotes
Heap (unordered)scan all blocks (O(n))append, cheapno ordering
Sorted (sequential)binary search O(log n) blocksexpensive (maintain order)good for range/olap
HashO(1) expected on keycheapno range queries, good exact-match

Blocking factor bfr = ⌊block_size / (record_size)⌋ records per block. Number of blocks for n records = ⌈n / bfr⌉. These two numbers drive most file-organisation numericals and re-appear in B-tree sizing.

Clustered vs unclustered (secondary) index
  • Clustered (primary) index: file records are physically stored in the key order of the index. Only one clustered index per file. Records with equal keys are adjacent → efficient range scans.
  • Unclustered (secondary) index: separate structure; each index entry points to a record that may be anywhere → possibly one block read per matching record.
  • Blocking factor and index "order" (pointers per node) are computed the same way in both, but range-query cost differs (clustered ≈ number of blocks; unclustered ≈ number of records).
GATE trap
For an unclustered index, a range query that returns k records can cost k block reads (one per record), while the same query on a clustered index reads about ⌈k/bfr⌉ blocks. Swapping these two estimates is a classic error. Also remember only one clustered index per file is possible.

Indexing — B & B+ Trees

B-tree Structure & Order Calculations

A B-tree of order m (each node holds at most m pointers) stores keys in both internal and leaf nodes.

B-tree sizing rules (order m)
  • Max children per node = m; max keys per node = m − 1.
  • Non-root internal (and leaf) node: at least ⌈m/2⌉ children → at least ⌈m/2⌉ − 1 keys.
  • Root: at least 2 children (0 or >0 keys); when full has m−1 keys.
  • All leaves at the same depth; every node at least half full.
  • Max keys over h levels: mh − 1.
  • Order from block size: solve m·(block_ptr) + (m−1)·(key_size) ≤ block_size.
Worked example — compute the order from a block size

Block = 2048 bytes. Key size = 9 B, block pointer = 6 B.
m·6 + (m−1)·9 ≤ 2048 → 6m + 9m − 9 ≤ 2048 → 15m ≤ 2057 → m ≤ 137.13.
Order m = 137 (largest integer satisfying the inequality). Keys per node = 136.

GATE trap
Two classic slips: (1) taking m (pointers) as the keys per node and off-by-one all parts; (2) forgetting that if the record pointer plus key must fit, the leaf computation differs from the internal-node computation. Write m×ptr + (m−1)×key ≤ block explicitly every time instead of trusting an instinctive number.

B+ Tree — Data in Leaves Only

In a B+ tree (the DBMS-favourite): internal nodes hold only keys and pointers (routing), all data records live in the leaves, and leaves are chained for fast range scans.

FeatureB-treeB+ tree
Data locationin internal and leaf nodesleaves only
Leaf chainnoyes (linked leaves)
Range querywalk the tree repeatedlyscan leaf chain
Space per nodeduplicates keyscompact internal nodes → higher fan-out
Height for given datausually tallerusually shorter / shallower
B+ node-count computations
  • Leaf capacity L = ⌊(block − next-leaf-ptr)/(key + record_ptr)⌋ records per leaf.
  • Number of leaves = ⌈R / L⌉.
  • Fan-out (internal order) = solve m·block_ptr + (m−1)·key ≤ block.
  • Number of levels (tree height) = ⌈logm(#leaves)⌉ + 1.
  • Block reads to find one record = tree height.
Worked example — how many block reads for R = 1,000,000 records?

Block = 2048 B; key = 9 B; record ptr = 7 B; block ptr = 6 B.

Leaf capacity L = ⌊(2048 − 6)/(9 + 7)⌋ = ⌊2042/16⌋ = 127.
Leaf count = ⌈1000000/127⌉ = 7874.
Internal order m: 6m + (m−1)·9 ≤ 2048 → 15m ≤ 2057 → m = 137.
Levels: root + ceiling internal levels = ⌈log137(7874)⌉ + 1 = ⌈1.83⌉ + 1 = 2 + 1 = 3 levels.
So fetching one record costs 3 block reads (root + 1 internal + 1 leaf).

GATE trap
B+ questions are about leaves and levels, B-tree questions about keys and order. Reusing the wrong formula (e.g. computing B+ leaf count with B-tree's m−1-key rule) produces a sky-high wrong answer. Also remember B+ range scans walk the leaf chain, not the height — two different cost figures.

Transactions, Serialisability & Concurrency

ACID, Schedules & Conflict Serialisability

A transaction is a sequence of operations (r = read, w = write, followed by commit c / abort a). The set of all operations of concurrent transactions in execution order is a schedule.

ACID
Atomicity (all-or-nothing) · Consistency (valid DB state) · Isolation (concurrent result equals some serial result) · Durability (committed data survives). The "I" is what concurrency control enforces.

Two operations conflict if they belong to different transactions, act on the same data item, and at least one is a write. A schedule is conflict serialisable if it can be made serial by swapping adjacent non-conflicting operations; equivalently its precedence graph has no cycle.

Worked example — is this schedule conflict serialisable?

Schedule: r1(A); r2(B); w1(B); w2(A);
Conflicts: r1(A) & w2(A) → r1 before w2 ⇒ edge T1→T2.
r2(B) & w1(B) → r2 before w1 ⇒ edge T2→T1.

Precedence graph has a cycle T1→T2→T1 ⇒ NOT conflict serialisable. (Equivalent to the classic "lost/cross write" that confuses the two orders.)

GATE trap
Only write**vs**write, write-vs-read, read-vs-write pairs on the same data item conflict. Read-read never conflicts. Students draw a precedence edge for every touched item (wrong) or forget that even two reads do not conflict. Build the graph only from genuine conflicts.

Locking Protocols & 2PL

Concurrency control restricts interleavings. The classic protocol is locking with shared (S, read) and exclusive (X, write) locks. A lock compatibility matrix:

Requested ↓ / Held →SX
Sgrantdeny
Xdenydeny
  • 2PL (two-phase locking): every transaction has a growing phase (only acquire locks) followed by a shrinking phase (only release locks); the two never interleave.
  • 2PL  ⟹  conflict serialisable, but is not deadlock-free nor cascadeless.
  • Strict 2PL: release all locks only at commit/abort → avoids cascading aborts.
  • Rigorous 2PL: hold locks until commit (strongest).
Locking tests
  • 2PL check: locate the first unlock and the last lock of each transaction; if any lock comes after an unlock of the same transaction → not 2PL (also if it re-locks after a release).
  • Serialisability ⟸ 2PL, not the converse.
  • Deadlock possible under 2PL even with compatible matrices properly applied (wait-for cycles).
Worked example — is this schedule 2PL?

T1: LOCK(A); r(A); UNLOCK(A); LOCK(B); w(B); UNLOCK(B).

The first unlock (UNLOCK(A)) occurs before the later LOCK(B). Growing (locks) and shrinking (unlocks) thus interleave for T1 ⇒ not 2PL. A valid 2PL schedule would acquire A and B first, then release both in the shrinking phase.

GATE trap
2PL guarantees serialisability but not deadlock freedom and (plain 2PL) not cascadelessness. Students answer "yes, deadlock-free" to a 2PL-is-serialisable question. Only strict/rigorous 2PL removes cascading aborts.

Isolation Levels, Graphed Schedules & Recovery

Isolation levelDirty read?Non-repeatable read?Phantom?
Read UncommittedYesYesYes
Read CommittedNoYesYes
Repeatable ReadNoNoYes
SerializableNoNoNo
Lock-based rules for these levels
  • Read Committed = S-locks released on read; X-locks held to commit.
  • Repeatable Read = S-locks held to commit; X-locks to commit.
  • Serializable = RR + predicate/range locks to block phantoms.
  • Recovery: write-ahead logging (WAL) — a log record must be flushed to disk before the dirty page is.
Anomaly cheat-sheet
A phantom is a newly-inserted row appearing inside an already-seen range (kills serialisability at Repeatable Read). Dirty read = reading uncommitted data (killed at Read Committed). Non-repeatable read = same row read twice with a different value (killed at Repeatable Read).
GATE trap
Order of strength is Serializable > RR > RC > RU. "Repeatable Read blocks non-repeatable reads but not phantoms" is the fact students most often invert. Also, under WAL the log precedes the data flush — students often reverse this single directional point.

Where students lose marks & how to avoid it

  • B-/B+-tree off-by-one: always state the order from m·ptr + (m−1)·key ≤ block; don't "eyeball" the fan-out.
  • Dedup in π and NULL handling in SQL: COUNT and projection are set-based; re-check what gets dropped.
  • Skipping the prime-attribute check — the 3NF-prime escape turns a "BCNF" into a "3NF" question.
  • NOT IN vs NOT EXISTS on NULLs — a single nested query can flip the whole answer.

What to skip / deprioritise under 25% time pressure

  • Long handwritten relational-algebra derivation if a compact SQL/logic equivalent answers the same mark.
  • Tuple-calculus traces on complex ∀/∃ formulas — low frequency, often 0.5-mark, and error-prone.
  • Deep file-parameter arithmetic beyond the blocking factor — the ≤1 mark it replaces is better spent on B+ tree and normalisation.
