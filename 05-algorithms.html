Asymptotic Complexity & Recurrences

Big-O family & loop analysis

The asymptotic classes bound growth up to constants for large n. Upper bounds use O, lower bounds use Ω, and tight (both) use Θ.

NotationMeansIntuition
f = O(g)f(n) ≤ c·g(n) for n ≥ n₀f grows no faster than g
f = Ω(g)f(n) ≥ c·g(n) for n ≥ n₀f grows no slower than g
f = Θ(g)both O(g) and Ω(g)f and g grow at the same rate
f = o(g)f/g → 0f is strictly slower than g
f = ω(g)f/g → ∞f is strictly faster than g
Growth-rate ordering (slowest → fastest)
Θ(1) < Θ(log n) < Θ(√n) < Θ(n) < Θ(n log n) < Θ(n²) < Θ(n³) < Θ(2ⁿ) < Θ(n!) < Θ(nⁿ)
A polynomial is always slower than any exponential: nk = O(2n) for any constant k.

Reading complexity out of code

  • Single loop running n times on constant work → Θ(n).
  • Nested loops i and j both to n → Θ(n²).
  • Halving loop (n, n/2, n/4, …) → Θ(log n) iterations.
  • Loop with 2 pointers / binary search → Θ(log n) per step.
  • i = i·2 → ⌈log₂n⌉ iterations; i = i·3 → ⌈log₃n⌉.
  • i² pattern (for i in 1..√n) → Θ(√n).
Handy log facts
logba = log a / log b = 1 / logab · alogbc = clogba · (1/2)log₂n = 1/n · log(n!) = Θ(n log n)
Worked example — complexity of three nested loops

Code: for i in 1..n: for j in 1..i: for k in 1..j: print(i)

Number of prints = Σₖ Σⱼ Σᵢ = Σₖ Σⱼ (n) inside, but count exactly: the innermost body runs Σi=1..n Σj=1..i j times.

Σj=1..i j = i(i+1)/2 ≈ i²/2. Σi=1..n i²/2 = n(n+1)(2n+1)/12 ≈ n³/6.

So total work = Θ(n³). Pattern to spot: i nested loops to n ⇒ often Θ(ni); verify the bounds grow.

GATE trap
O and Ω are one-sided. "O(n)" means at-worst n — a constant-time algorithm is also O(n). Question options that say "the only bound is Θ(n)" are typically wrong. Also, "best case of Insertion sort is O(1)" is sloppy: a single pass is O(n). Always state which case (best/worst/average) the complexity refers to — GATE almost always fixes this in the stem, so respect it.

Solving recurrences (Master theorem, substitution)

1. Master theorem

T(n) = a·T(n/b) + f(n), a ≥ 1, b > 1
Compare f(n) with nlogba (call it nc, c = logba):
  • Case 1: f(n) = O(nc−ε) → T(n) = Θ(nc)  (work dominates at leaves)
  • Case 2: f(n) = Θ(nc) → T(n) = Θ(nc log n)
  • Case 3: f(n) = Ω(nc+ε) and a·f(n/b) ≤ k·f(n) for k<1 → T(n) = Θ(f(n))  (work dominates at root)
When f(n) = Θ(nd): compare d with c = logba → cases 1/2/3 in that order.

2. Substitution method

  1. Guess the form (e.g. T(n) = O(n log n)).
  2. Induct: assume it holds for smaller sizes, substitute the induction hypothesis into T(n) = a·T(n/b) + f(n).
  3. Bound the leftover and verify constants don't blow up.

3. Recursion tree

Draw the tree: level cost × number of levels. alevel nodes each with cost f(n/blevel). Sum over levels. Useful when the master theorem's conditions don't apply (e.g. f(n) is a "swimming" function like n/log n).

Worked example — T(n) = 3T(n/2) + n²

a = 3, b = 2, c = log₂3 ≈ 1.585, d = 2 (from n²). d > c → Case 3.

Check regularity: a·f(n/b) = 3·(n/2)² = (3/4)n² ≤ k·n² for k = 3/4 < 1 ✓.

So T(n) = Θ(n²). The polynomial divide cost dominates the exponential leaf count.

Worked example — T(n) = 2T(n/2) + n/log n (master theorem does not apply)

a = 2, b = 2, c = 1, f(n) = n/log n. This is Θ(n/log n), which is between nc−ε and nc — a "gap" the master theorem cannot handle.

Recursion tree: level k has 2k nodes each costing (n/2k)/log(n/2k). Per level cost ≈ n/(log n − k).

Summing ≈ n · [1/log n + 1/(log n −1) + … + 1/1] = Θ(n log log n).

Lesson: know when to abandon the master theorem — this exact shape is a known GATE trick.

GATE trap
Case 3 needs the regularity condition a·f(n/b) ≤ c·f(n). Many questions give a recurrence like T(n) = 2T(n/2) + n/log²n where the two sides look comparable but the master theorem silently does not apply. Do not force it — switch to the recursion tree.

Sorting

Comparison-based sorting

AlgorithmBestWorstAvgStableIn-placeNotes
InsertionO(n)O(n²)O(n²)YesYesgreat on near-sorted input
BubbleO(n)O(n²)O(n²)YesYesrarely used
SelectionO(n²)O(n²)O(n²)NoYesalways n² even if sorted
MergeO(n log n)O(n log n)O(n log n)YesNo (O(n) aux)stable, external-friendly
QuickO(n log n)O(n²)O(n log n)NoYesworst when input sorted + bad pivot
HeapO(n log n)O(n log n)O(n log n)NoYesno worst-case blow-up
Sorting decision tree = lower bound
Any comparison-based sort must make Ω(n log n) comparisons in the worst case: a binary decision tree over n! outcomes needs height ≥ ⌈log₂(n!)⌉ = Ω(n log n).
Optimal (reach the bound): Merge and Heap sort. Quick is optimal on average, not worst case.

Pivot pathologies in Quick sort

  • First element as pivot + sorted/almost-sorted input → worst case O(n²).
  • First element as pivot + reverse-sorted → also worst case.
  • Random pivot or median-of-three → expected O(n log n) on all inputs.
  • Choosing the median as pivot for every partition → always O(n log n).
GATE trap
Stability is input-sensitive, not a fixed property of every implementation. Quick sort is usually called unstable, but an implementation that partitions keys only ("key, tag" with original index) is stable. Also Insertion sort's O(n) best case needs an already-sorted or nearly-sorted array — on a random array it is O(n²) just like Bubble/Selection.
Worked example — apply Insertion sort to [5,2,4,6,1,3]

Take each element and insert into the sorted prefix:

[5] | 2 → [2,5] | 4 → [2,4,5] | 6 → [2,4,5,6] | 1 → [1,2,4,5,6] | 3 → [1,2,3,4,5,6]

5 comparisons-and-shifts on this near-random list illustrate that Insertion sort is Θ(n²) in the worst case but only Θ(n) when the input starts sorted (each new element stays put).

Non-comparison sorting & order statistics

Linear sorts beat the n log n bound because they are not comparison-based — they exploit the structure of keys.

AlgorithmTimeSpaceStableRequirement
CountingO(n + k)O(n + k)Yeskeys in small range 0..k
RadixO(d·(n + k))O(n + k)Yes (if each pass stable)digits d, base k
Bucketavg O(n)O(n)Yesuniformly distributed keys
Radix sort complexity
Sort d passes of base k: O(d·(n + k)) time, O(n + k) space. For integers with b bits, d = b/k passes. With k = n and d small, it behaves like O(n).

Order statistics (selection)

  • Naive: find k-th smallest by sorting → O(n log n).
  • Quick-select (randomised partition, recurse on one side): expected O(n), worst O(n²).
  • Median-of-medians: deterministic O(n) worst case (partitions into 5-groups, guarantees 3n/10 drop).
GATE trap
Counting/Radix are not comparisons — so the Ω(n log n) lower bound does not apply to them. A question claiming "no sort can beat O(n log n)" is only true within comparison-based sorting. Also, Radix sort is only correct if each digit pass is a stable sort (usually counting sort).

Searching & Hashing

Searching & binary search

  • Linear search: O(n) worst, O(1) best; works on any array.
  • Binary search: O(log n), needs a sorted array and an ordering predicate.
  • Ternary search: O(log₃n) comparisons on unimodal functions (not for sorted search).
  • Interpolation search: expected O(log log n) on uniform data, worst O(n).
Binary search invariants
For sorted array of size n, worst-case comparisons = ⌊log₂n⌋ + 1. Find largest element < x / smallest ≥ x ("floor/ceiling") by adjusting hi/lo correctly — the classic off-by-one trap. Termination always at hi ≥ lo.
Worked example — search for 23 in [3,7,12,23,40,45,58]

lo=0, hi=6. mid = ⌊(0+6)/2⌋ = 3 → a[3] = 23. Found in 1 comparison. Hitting the middle trivially is rare; run a longer one:

Search 40: mid=3 (23 < 40 → lo=4). mid=⌊(4+6)/2⌋=5 → a[5]=45 > 40 → hi=4. mid=4 → a[4]=40 ✓. 3 comparisons, log₂7 ≈ 2.8 ✓ consistent with ⌊log₂n⌋+1 = 3.

GATE trap
Binary search requires the array be sorted — but GATE often asks for the number of comparisons up to termination including the "not found" run. On an odd/even-length array the first mid can be mistaken; always count the failed cases too. For n = 2k the worst case is exactly k+1 comparisons.

Hashing & hash tables

A hash table stores item where h(key) says. Performance depends on the load factor α = n/m (items / slots) and the collision policy.

Collision resolution

MethodWorst-case searchTypical behaviourNotes
Chaining (linked lists)O(n)O(1 + α)all keys can collide into one chain
Open addressing (linear probing)O(n)O(1 + 1/(1−α))primary clustering problem
Double hashingO(n)O(1/(1−α))best open-addressing probing
Hash-table facts worth memorising
Expected cost for a successful/unlucky search with chaining: O(1 + α).
Linear probing degenerates and shows primary clustering (long runs of filled slots).
α < 0.5 is typical for open addressing; tables are resized (rehash) when α exceeds a bound.
A good hash distributes keys uniformly; a poor one makes every operation O(n).
Worked example — least collisions for keys into 4 slots

Insert 5 elements into 4-slot table with linear probing, h(k) = k mod 4. Keys 4, 8, 12, 16, 20:

All map to slot 4 mod 4 = 0 → the entire array becomes one long cluster. Search for any of them is O(5), the worst case.

Contrast: if the hash were h(k) = k mod 4 but keys were 0,1,2,3,4 and probing cyclic, you see how the hash function, not the table, decides the worst case. This is why "hashing is O(1)" is false as a blanket claim — it is O(1) average, O(n) worst.

GATE trap
Hashing average O(1), worst O(n). The option "search is always O(1)" is wrong. Also, deleting an element in open addressing requires a tombstone (mark, not empty) or searches break the probe chain — a favourite subtle point.

Divide & Conquer

D&C strategy & examples

Divide → recurse → combine. The combination step decides whether the method pays off. Works when the problem splits into independent subproblems (so results merge cleanly).

AlgorithmRecurrenceComplexity
Merge sortT(n) = 2T(n/2) + nΘ(n log n)
Quick sort (average)T(n) = 2T(n/2) + nΘ(n log n)
Strassen's matrix multiplyT(n) = 7T(n/2) + n²Θ(nlog₂7) ≈ Θ(n2.807)
Binary searchT(n) = T(n/2) + 1Θ(log n)
Closest pair of pointsT(n) = 2T(n/2) + nΘ(n log n)
Karatsuba multiplyT(n) = 3T(n/2) + nΘ(nlog₂3) ≈ Θ(n1.585)
D&C complexity heuristic
For T(n) = aT(n/b) + f(n): if you split into more problems than the halves can absorb (e.g. 7 subproblems for matrix multiply), the leaf count alogₙ = nlogba can beat the naive method. Strassen, Karatsuba and the Fast Fourier Transform (FFT, T(n)=2T(n/2)+n with clever combine → O(n log n)) all exploit this.
GATE trap
D&C is not always better: for the closest-pair problem the naive combine is O(n²), and it only wins because the combine step is cleverly pruned to O(n). The combine step dominates — memorise that D&C complexity is determined by a (leaf growth) vs f(n) (combine cost). Strassen beats naive when n is large enough for constant factors to amortise, not for tiny n.
Worked example — why Merge sort is stable-list at O(n log n)

Split recursively until singletons, then merge: compare heads of the two sorted runs, taking the smaller. The merge of two n/2 lists is O(n), and there are log₂n levels → O(n log n).

Merge is stable because when equal keys appear in left and right runs, we take the left one first, preserving input order — the reason GATE lists Merge as the go-to stable sort.

Greedy Algorithms

Greedy strategy & classic problems

Greedy makes the locally optimal choice at each step and never undoes it. It works only when the problem has a greedy-choice property (local choice extends to a global optimum) plus optimal substructure.

ProblemGreedy choiceOptimal?
Activity selectionpick earliest-finishingYes (exchange argument)
Fractional knapsackhighest value/weight ratioYes
Huffman codingmerge two least-frequentYes (prefix codes)
0/1 knapsackratio by itemNo — use DP
Coin changelargest coin ≤ remainderOnly for canonical sets
Minimum spanning treelightest safe edgeYes (Kruskal/Prim)
Single-source shortest path (no negative)nearest unvisitedYes (Dijkstra)
GATE trap
Greedy fails exactly when the problem lacks the greedy-choice property. The two killer examples: 0/1 knapsack (ratio greedy is wrong — an item you skip for size reasons may be needed for weight reasons) and coin change (greedy needs a canonical coin system — {1,5,10} works, {1,3,4} does not: amount 6 → greedy 4+1+1 = 3 coins, optimal 3+3 = 2). Examiners ask "which technique solves X correctly?" using DP for these two.
Worked example — Huffman coding for A, B, C, D with freqs 5, 9, 12, 13

Merge the two lowest: (5,9) → 14. Now leaves {12,13,14}. Merge (12,13) → 25. Merge (14,25) → 39.

Code lengths: A and B get depth 2 (each contributed to the 14 node), C and D depth 2, so total bits: 2·5 + 2·9 + 2·12 + 2·13 = 78. (An equal-depth result here because freqs are close.)

Rule: Huffman(total) = Σ freq × depth — it is optimal because no other prefix code can beat it (a greedy proof by exchange argument).

Worked example — activity selection greedy proof step

Claim: picking the interval with the earliest finish time is always safe.

Suppose an optimal solution starts with interval J. Let I be the earliest-finishing interval. Since finish(I) ≤ finish(J), we can swap J for I without crowding out any later activity — I ends no later than J, so all activities after J still fit after I.

This exchange argument (also used for MST) is the standard GATE-style proof that a greedy choice is safe. You'll be asked "why is this greedy correct?" — the answer is always: local choice + exchange argument + optimal substructure.

Shortcut — DP vs greedy in one line
If you can take fractions of an item (knapsack, resource) → greedy. If items are all-or-nothing/indivisible and choices affect each other → DP. If the decision is an ordering (schedule, code) where local choice never hurts → greedy.

Dynamic Programming

DP principle: two key properties

DP works when a problem has optimal substructure (optimal solution built from optimal solutions of subproblems) and overlapping subproblems (same subproblem solved repeatedly). Solve each subproblem once, store it, reuse.

VariantMechanismSpaceWhen to choose
Naive recursionrecompute everythingcall stacknever for overlapping problems
Memoisation (top-down)recurse, cache resultsO(dim × entry)only some subproblems needed
Tabulation (bottom-up)fill table in dependency orderO(table size)most/ all subproblems used
Classic DP recurrences (memorise)
0/1 knapsack: K(i,w) = max(K(i−1,w), vᵢ + K(i−1, w−wᵢ)) — O(n·W) time & space.
LCS: if Xᵢ = Yⱼ then L(i,j) = 1 + L(i−1,j−1), else max(L(i−1,j), L(i,j−1)) — O(m·n).
Matrix-chain: m[i,j] = mink(m[i,k] + m[k+1,j] + pi−1pkpj) — O(n³).
Coin change (min coins): dp[w] = min(dp[w − c] + 1 for c in coins) — O(n·W).
Rod cutting: r[n] = max(p[n], maxk(r[k] + r[n−k])) — O(n²).
Shortest path in DAG / Bellman–Ford: DP over relaxed estimate.
Worked example — LCS table for X="ABCBDAB", Y="BDCABA"

Build (m+1)×(n+1) table: L(i,0)=L(0,j)=0. Fill either 1+L above-left on match, else max(left,above).

The maximum value in the bottom-right cell = length 4 (e.g. "BCBA" or "BDAB").

DP properties visible: optimal substructure (a longer common subseq extends a shorter one) and overlapping subproblems (same L(i,j) requested from many paths) — hence the table, not brute force over all subsequences (O(2m)).

Worked example — 0/1 knapsack with capacity 5, items (w,v): (2,3),(3,4),(4,5),(5,6)

DP over items × capacity. Fill K(i,w) = max(skip item i, take item i + best with remaining capacity).

Items sorted: (2,3): K(1,2..5)=3. (3,4): K(2,3)=4, K(2,5)=max(4, 4+K(1,2)=7)=7. (4,5): K(3,4)=5, K(3,5)=max(5, 5+K(2,1)=5)=5. (5,6): K(4,5)=max(6, 6+K(3,0)=6)=6.

Optimal = 7 (items 2+3 hold capacity 5, value 4+3). Greedy-by-ratio would instead pick (5,6) then be stuck → value 6 — this is why 0/1 knapsack needs DP.

GATE trap
Optimal substructure alone is not enough — you also need overlapping subproblems for DP to help. Shortest path has optimal substructure but is not greedy-correct in general graphs (Dijkstra fails with negative edges) and DP is not the tool for every "compound" decision. Also the classic: 0/1 knapsack is pseudo-polynomial O(n·W) — W in the table is the numeric capacity, so it is polynomial only when W is polynomial in the input bit-length; with W = 2ⁿ it is exponential.

Graph Traversals (BFS & DFS)

Representation & elementary facts

RepresentationSpaceEdge check (u,v)Iterate neighbours
Adjacency matrixO(V²)O(1)O(V)

Memory trade-off
Adjacency matrix: O(V²) always — dense-friendly, fast edge lookup.
Adjacency list: O(V + E) — sparse-friendly, cheap neighbour iteration.
BFS/DFS cost: O(V + E) with an adjacency list, O(V²) with a matrix.
GATE trap
The traversal is O(V+E) only with an adjacency list. With an adjacency matrix, checking neighbours of every vertex is O(V) each → total O(V²). Cubic algorithms on dense graphs (O(V²)) are usually stated with the matrix; read the representation before answering.

BFS

BFS explores level by level using a queue. It discovers vertices in order of distance from the source and gives the shortest-path distance in an unweighted graph.

  • Uses a queue (FIFO); marks vertices on discovery.
  • Time O(V + E); distance d[v] = number of edges from source.
  • Produces a BFS tree of shortest paths (unweighted).
  • Applications: shortest path in unweighted graph, BFS layers, bipartiteness check.
BFS bipartite test
An undirected graph is bipartite ⇔ BFS finds a BFS tree with no edge between two vertices of the same level parity (i.e. no "cross edge" of odd length). A graph with an odd cycle is not bipartite.

DFS & applications

DFS explores as deep as possible then backtracks, using a stack (explicit or recursion).

ApplicationRequiresResult
Cycle detection (directed)a "grey"/on-stack markback edge ⇔ cycle exists
Topological sortDAG + reversed finish ordera valid linear order
Connected components (undirected)run DFS per undiscovered vertexcount of CCs
Strongly connected componentsKosaraju (2×DFS) / TarjanSCC decomposition, O(V+E)
Topological sort
Topological sort exists iff the graph is a DAG. DFS-based: output vertices in reverse order of finishing time = O(V + E). A topological order does not have to be unique.
GATE trap
In a directed graph, a back edge (to a vertex currently on the DFS stack) ⇔ a cycle. But in an undirected graph, an edge to any discovered vertex (back or cross) indicates a cycle — do not apply the directed rule blindly. Also, topological sort does not exist for cyclic graphs, and a graph can have >1 valid topological order.
Worked example — DFS finish times give topological order

Graph edges: A→B, A→C, B→D, C→D. DFS from A: visit A(discover), B, D (D finishes), B finishes, C, then D already seen (cross/forward), C finishes, A finishes.

Finish order (increasing): D, B, C, A. Reverse finish order = A, C, B, D — a valid topological sort: every edge points from earlier to later (A→B: A before B ✓, A→C ✓, B→D ✓, C→D ✓).

Note C→D and B→D both finish D first because D is a sink; this is why topological order = reverse of finish time.

Minimum Spanning Trees

Kruskal & Prim

AlgorithmCore ideaData structureComplexity
Kruskaltake globally lightest edge not creating a cycleUnion–Find / sort edgesO(E log E) = O(E log V)
Primgrow one tree by lightest edge from itpriority queue of frontierO(E log V) with a heap; O(V²) with dense matrix
Cut property (correctness of both)
For any cut (S, V−S), the lightest crossing edge is in some MST.
Cycle property: the heaviest edge on a cycle is never in any MST.
These two facts justify Kruskal and Prim: each only ever adds a "safe" light edge across a cut.
GATE trap
The MST is not always unique. If all edge weights are distinct, the MST is unique. With ties, different MSTs are possible, but they all have the same total weight. Also Prim's grows a single tree and needs a connected graph; Kruskal works on disconnected graphs and yields a minimum spanning forest. "Prim needs the lightest edge of the whole graph first" is false — it starts from any vertex.
Worked example — Kruskal on a 4-node square, weights 1,1,2,2,3 (cycle)

Vertices a,b,c,d; edges a–b=1, c–d=1, a–c=2, b–d=2, b–c=3, a–d=4 (a square with a diagonal).

Sort: (a–b,1) add; (c–d,1) add; (a–c,2) add (no cycle: connects a to c); (b–d,2) — b,d already connected via a–c–…–d? a–b and c–d and a–c give path b–a–c–d, so b–d creates a cycle → skip; (b–c,3) creates cycle → skip; (a–d,4) skip.

MST edges: a–b, c–d, a–c. Total = 1+1+2 = 4. Three edges = V−1 = 3 for 4 vertices ✓ — always check you have V−1 edges.

Pick Prim if…
The graph is dense (E ≈ V²) — use the O(V²) matrix form of Prim. Pick Kruskal if the edges are already sorted or you only need the total weight (no adjacency structure needed).

Shortest Paths

Single-source: Dijkstra & Bellman–Ford

AlgorithmCostEdge weightsDetects neg. cycle?
DijkstraO(E log V) heap / O(V²) matrixnon-negative onlyNo — fails outright
Bellman–FordO(V·E)any, incl. negativeYes (in V-th iteration)
Dijkstra correctness premise
Dijkstra is greedy: repeatedly settle the nearest unsettled vertex. It is correct iff all edge weights ≥ 0 (then a settled vertex's distance is final). Negative weights can make a later edge lower a distance that was already settled — so Dijkstra's answer becomes wrong, though it still runs. Bellman–Ford relaxes all edges V−1 times: after the (V−1)-th pass all reachable distances are exact; an edge still relaxable on pass V means a negative-weight cycle exists.
GATE trap
Dijkstra does not "crash" on negative edges — it silently returns a wrong answer (unless the graph has a negative cycle reachable from the source, in which case no finite shortest path exists at all). Many questions test exactly this: "which algorithm correctly finds shortest path with negative weights?" → Bellman–Ford (and ≤ no negative cycle). Negative cycle → no algorithm gives a finite path; Bellman–Ford only detects it.
Worked example — Dijkstra on a→b=4, a→c=1, c→b=2, c→d=3

Start a=0. Settle a; relax b=4, c=1. Settle c (1); relax b via c = 1+2 = 3 < 4 → b=3, d = 1+3 = 4. Settle b(3). Settle d(4).

Final distances: a=0, c=1, b=3, d=4. Path a→c→b→d. Note how c was settled before b even though b had a direct edge — the greedy choice is the nearest unsettled, not the nearest unscanned edge.

Worked example — Bellman–Ford detects negative cycle

Graph: a→b=−1, b→c=−1, c→a=−1 (a 3-cycle, sum = −3 < 0). Any source: relax over V−1 = 2 passes, then attempt pass 3.

Distances keep decreasing every pass — there is no termination; a negative-weight cycle is present, so no shortest path exists (you can loop forever to reduce cost). Bellman–Ford reports it on the V-th pass. Contrast: if the same edges were +1, +1, +1 the cycle is positive and the shortest path is well-defined and finite.

All-pairs: Floyd–Warshall & transitive closure

Floyd–Warshall finds shortest paths between every pair. Let D(k) be shortest paths using intermediates only from {1..k}.

Floyd–Warshall recurrence
D(k)[i][j] = min( D(k−1)[i][j], D(k−1)[i][k] + D(k−1)[k][j] )
Two nested inner loops over all i,j for each k → O(V³); space O(V²). Handles negative edge weights, and a negative cycle shows as D[i][i] < 0.

Transitive closure (reachability) is the same table but boolean: keep reachable[k][i][j] with OR instead of min → O(V³) time, O(V²) space.

GATE trap
Floyd–Warshall runs in O(V³) time but O(V²) space — do not confuse them. Also it computes all-pairs; for a single source it is wasteful (Dijkstra/Bellman–Ford are better). "Which algorithm gives all-pairs shortest paths?" → Floyd–Warshall (or repeated Dijkstra when weights ≥ 0: O(V·E log V) — often the faster choice on sparse graphs).
Worked example — run transitive closure topologically

Start from reach[i][j] = adjacency. For k in order, set reach[i][j] |= reach[i][k] && reach[k][j].

On a 3-node chain A→B→C: after k=B, reach[A][C] becomes true (A→B and B→C). The k loop must run increasingly so multi-hop paths compose; running k topologically is what lets reachability propagate through the table in-place safely.

The GATE decision checklist for technique questions
  1. Can a small input break the "obvious" greedy? (0/1 knapsack, coin change) → then it's DP.
  2. Negative edge weights in a shortest-path question? → not Dijkstra → Bellman–Ford / Floyd–Warshall.
  3. Weights distinct? → MST unique. Tied? → several MSTs, same total weight.
  4. Unweighted graph & path length in edges? → BFS.
  5. Reachability / all-pairs? → Floyd–Warshall O(V³) or transitive closure.
  6. In a directed graph asking for sorted order? → topological sort (DAG only).
Common time sinks — cut these first
  • Recomputing a full DP table when the answer is the recurrence itself.
  • Running Floyd–Warshall/Warshall by hand on a large graph — instead test one edge case.
  • Re-deriving a stability table from memory instead of trusting the memorised sheet.
  • Over-interpreting an "always/never" option — test the smallest counterexample (2 vertices, 1 edge).
